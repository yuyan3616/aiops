# v8.1.1 History MVP Spec

> Status: implementation baseline
> Parent: v8.1 Controlled Harness
> Purpose: restore the original Pi Chat persistence model for RCA investigations before the broader v8.2 Audit/Resume work.

## 1. Goal

v8.1.1 must make RCA investigations behave like normal Pi Chat history:

```text
run RCA
-> investigation appears in real history
-> Pi Agent sessions are persisted as JSONL
-> stop/restart Node server
-> history still exists
-> open an old investigation
-> previous RCA messages/tasks/evidence/hypotheses/conclusion are visible
```

## 2. Design principle

Reuse Pi Chat's proven split instead of inventing another transcript store:

```text
Pi SessionManager JSONL
  -> Coordinator / Log / Metric / Trace / Context transcript

RCA InvestigationRepository JSON record
  -> investigation metadata + current RCA snapshot + Pi session references
```

The Investigation record does not copy Pi transcript entries.

## 3. Local layout

Default root follows Pi Chat conventions:

```text
~/.pi/agent/pi-chat/rca/
├── investigations/
│   └── <investigationId>.json
├── sessions/
│   ├── coordinator-*.jsonl
│   ├── log-*.jsonl
│   ├── metric-*.jsonl
│   ├── trace-*.jsonl
│   └── context-*.jsonl
└── workspaces/
    └── <investigationId>/
```

`PI_CHAT_ROOT_DIR` may override the Pi Chat root for tests/local isolation.

## 4. Investigation record

```ts
interface InvestigationRecord {
  version: 1;
  id: string;
  datasetTaskId: string;
  title: string;
  prompt: string;
  status: InvestigationStatus;
  createdAt: string;
  updatedAt: string;
  snapshot: PersistedInvestigationSnapshot;
  sessions: Partial<Record<RcaAgentRole, PiSessionRef>>;
}
```

A Pi session reference contains only `sessionId` and `sessionFile`.

## 5. Pi session lifecycle

For each role, create lazily with Pi native persistence:

```text
SessionManager.create(workspaceDir, sessionsDir, { id })
```

If the Investigation record already has a valid session file:

```text
SessionManager.open(sessionFile, sessionsDir, workspaceDir)
```

No RCA path should use `SessionManager.inMemory()` for Coordinator/Specialist sessions.

## 6. History lifecycle

- `POST /api/rca/incidents` creates a new Investigation with a unique ID.
- `GET /api/rca/incidents` lists persisted real investigations sorted by `updatedAt`.
- `GET /api/rca/incidents/:id` opens a persisted Investigation snapshot.
- The server keeps an in-memory `RcaRuntime` only while the process is alive; the repository remains the source for history after restart.
- A persisted `running`/`stopping` Investigation loaded after process restart is displayed as `interrupted`; v8.1.1 does **not** automatically resume it.

## 7. Persistence cadence

RcaService subscribes to runtime events and persists the current snapshot using a small debounce. Important terminal events are flushed immediately.

The repository writes JSON atomically via temporary file + rename.

## 8. Frontend behavior

- Remove fake history entries.
- Left sidebar shows only persisted investigations.
- `新建排查` returns to welcome/recommendation state.
- Starting a new investigation first creates an Investigation, navigates/selects it, then starts RCA.
- Clicking a history item loads its persisted snapshot and binds SSE for that Investigation.

## 9. Explicit non-goals

- SQLite.
- Audit Timeline / append-only EventLog.
- automatic resume of interrupted tasks.
- completed Investigation fork / post-RCA Q&A.
- token-level resume.
- Evidence coverage reuse.
- benchmark evaluation.

Those remain v8.2+ work.

## 10. Acceptance

```text
A. run t039 once -> a real history item exists
B. five Agent roles that are actually used create Pi JSONL sessions
C. restart server -> history list still contains the Investigation
D. open history -> messages/tasks/evidence/hypotheses/conclusion are restored
E. fake payment-timeout/checkout-failed history is gone
F. no RCA AgentSession uses SessionManager.inMemory()
```
