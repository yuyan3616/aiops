# v8.1 Specification — Controlled Multi-Agent Investigation Harness

> Milestone: **v8.1**  
> Status: **implementation-ready**  
> Depends on: v8.0 RCA100 `t039` real-data loop  
> Roadmap: [`rca-harness-roadmap.md`](./rca-harness-roadmap.md)

## 1. Problem statement

v8.0 can run a real RCA investigation, but its execution Harness is intentionally lightweight:

- `delegate_agents` directly fans out through `Promise.all`;
- task lifecycle is implicit in Agent status;
- specialist context is assembled inline;
- timeout/tool-call/turn limits are mostly prompt-level conventions;
- cancellation does not yet propagate through the whole investigation tree;
- task tracing is not a first-class domain concept.

This is sufficient for a demo, but not enough to guarantee bounded and explainable execution.

v8.1 introduces a small runtime layer around Pi without replacing Pi AgentSession.

## 2. Goals

v8.1 MUST provide:

1. explicit `AgentTask` lifecycle;
2. deterministic scheduling rules;
3. hard execution budgets;
4. centralized context assembly;
5. cancellation propagation;
6. tool input/output guardrails;
7. investigation/task/tool tracing identifiers;
8. backward compatibility with the current RCA100 `t039` demo.

## 3. Non-goals

v8.1 MUST NOT add:

- database-backed persistence or resume;
- a generic message bus;
- distributed workers;
- Temporal/LangGraph/AutoGen runtime dependencies;
- semantic/vector retrieval;
- coverage/subset Evidence reuse;
- ground-truth evaluation;
- multiple RCA100 cases as a product requirement.

These belong to later milestones in the roadmap.

## 4. Target architecture

```text
Pi Coordinator AgentSession
       |
       | delegate_agents(assignments)
       v
InvestigationRuntime
       |
       v
TaskScheduler -------------------------+
       |                               |
       | creates / transitions         | cancellation
       v                               v
AgentTask                         AbortController
       |
       v
ContextBuilder
       |
       v
AgentManager
       |
       v
Pi Specialist AgentSession
       |
       v
BudgetGuard -> ToolGuard -> ToolGateway -> RCA100
       |                          |
       |                          v
       +--------------------> EvidenceStore

All lifecycle transitions -> EventChannel / trace metadata
```

## 5. Core domain types

### 5.1 AgentTask

```ts
export type AgentTaskStatus =
  | "queued"
  | "running"
  | "succeeded"
  | "failed"
  | "cancelled"
  | "timed_out";

export interface AgentTask {
  id: string;
  investigationId: string;
  runId: string;
  agent: AgentKind;

  instruction: string;
  service?: string;
  operation?: string;

  evidenceIds: string[];
  hypothesisIds: string[];

  policy: TaskPolicy;
  status: AgentTaskStatus;
  attempt: number;

  createdAt: string;
  startedAt?: string;
  completedAt?: string;

  result?: AgentTaskResult;
  error?: TaskError;
}
```

`AgentTask` is the unit of specialist work. It is not the same thing as a Pi Session and it is not a Tool Call.

### 5.2 AgentTaskResult

```ts
export interface AgentTaskResult {
  summary: string;
  evidenceIds: string[];
  toolCallCount: number;
  turnCount: number;
  durationMs: number;
}
```

The full Specialist transcript is not returned to the Coordinator.

### 5.3 TaskPolicy

Initial defaults:

```ts
export interface TaskPolicy {
  timeoutMs: number;      // default 60_000
  maxTurns: number;       // default 6
  maxToolCalls: number;   // default 10
  maxEvidence: number;    // default 12
  maxAttempts: number;    // default 1 in v8.1
}
```

`maxAttempts = 1` is intentional for v8.1. Pi already performs provider retry. Task-level rerun policy will remain conservative until error classification is proven.

Environment overrides MAY be added, but defaults must live in one server-side policy module.

## 6. Task state machine

Allowed transitions:

```text
queued -> running
queued -> cancelled

running -> succeeded
running -> failed
running -> cancelled
running -> timed_out
```

Terminal states MUST NOT transition again in v8.1.

A budget violation is represented as `failed` with a typed error code unless it is specifically a wall-clock timeout (`timed_out`).

## 7. TaskScheduler

### 7.1 Rules

1. One AgentSession MUST NOT execute two prompts concurrently.
2. Per Agent kind concurrency = `1`.
3. Global specialist concurrency default = `3`.
4. Different Agent kinds may run concurrently.
5. Tasks from one `delegate_agents` call MAY execute concurrently when scheduling permits.
6. Queued work MUST observe investigation cancellation before starting.

Example:

```text
Log task A ------+
                 +-- may run concurrently
Metric task C ---+

Log task B waits for Log task A because both share Log AgentSession semantics.
```

### 7.2 Implementation constraint

Do not add a general queue library unless necessary. A small keyed scheduler is preferred for v8.1.

Suggested location:

```text
server/rca/harness/task-scheduler.ts
```

## 8. ContextBuilder

### 8.1 Purpose

`ContextBuilder` owns cross-Agent context assembly. `AgentManager` must not manually concatenate arbitrary investigation state.

Suggested API:

```ts
buildSpecialistContext(input: {
  task: AgentTask;
  caseContext: CaseContext;
  hypotheses: HypothesisView[];
  evidence: EvidenceView[];
}): SpecialistExecutionContext
```

### 8.2 SpecialistExecutionContext

```ts
export interface SpecialistExecutionContext {
  case: {
    taskId: string;
    alertTitle: string;
    alertEntity?: string;
    startTime: string;
    endTime: string;
  };

  assignment: {
    taskId: string;
    instruction: string;
    service?: string;
    operation?: string;
  };

  hypotheses: Array<{
    id: string;
    title: string;
    state: HypothesisState;
  }>;

  evidence: EvidenceContextItem[];

  constraints: {
    timeoutMs: number;
    maxTurns: number;
    maxToolCalls: number;
    maxEvidence: number;
  };
}
```

### 8.3 Evidence selection in v8.1

Do NOT implement embeddings or semantic search.

Selection order:

1. Evidence explicitly referenced by `task.evidenceIds`.
2. Evidence supporting/rejecting `task.hypothesisIds`.
3. Recent Evidence matching task service/entity when inexpensive to determine.
4. Stop at `policy.maxEvidence`.

The builder returns compact Evidence summaries and IDs, never another Agent's transcript.

## 9. Coordinator delegation contract

Extend `delegate_agents` assignment schema to allow optional context references:

```ts
{
  agent: AgentKind;
  goal: string;
  service?: string;
  operation?: string;
  evidenceIds?: string[];
  hypothesisIds?: string[];
}
```

The Coordinator still decides **what** to investigate; the Harness decides **how** the task executes.

## 10. BudgetGuard

### 10.1 Tool-call budget

Every Specialist custom tool wrapper increments `toolCallCount` before execution.

If the next call would exceed `maxToolCalls`:

- reject the tool execution;
- abort/settle the specialist task;
- mark task `failed` with `TASK_TOOL_BUDGET_EXCEEDED`.

### 10.2 Turn budget

Track Pi session `turn_start` / `turn_end` events where available in 0.86.1.

If turns exceed `maxTurns`, abort the Session and mark:

```text
TASK_TURN_BUDGET_EXCEEDED
```

Do not implement context-token accounting in v8.1 unless Pi exposes a stable low-cost counter in the current runtime path.

### 10.3 Evidence budget

A task may create no more than `maxEvidence` Evidence records. Existing reused Evidence does not count as newly created Evidence.

## 11. Timeout

Each running task gets a wall-clock deadline.

Preferred semantics:

```text
TaskScheduler starts task
 -> start timeout timer
 -> AgentManager runs session
 -> timeout fires
 -> session.abort()
 -> task = timed_out
 -> terminal task event
```

Avoid wrapping with an un-cancelled `Promise.race` that leaves the Pi Session running in the background.

## 12. Cancellation propagation

### 12.1 Investigation-level controller

Each active run owns one `AbortController`.

```text
Investigation AbortController
   |- queued TaskScheduler entries
   |- running AgentTask
   |- AgentSession.abort()
   `- ToolGateway signal where backend supports cancellation
```

### 12.2 Abort API

Add an RCA endpoint equivalent to:

```text
POST /api/rca/incidents/:id/abort
```

Behavior:

- idle/completed -> no-op success;
- running -> mark Investigation stopping/cancelled according to shared status model;
- queued tasks -> cancelled;
- running tasks -> session abort;
- no new tasks accepted after abort signal.

Frontend MAY expose the existing rerun action as a stop control while running, or add a dedicated stop button. Keep the UI minimal and Pi-chat aligned.

## 13. ToolGuard

The current Tool Gateway ACL remains and becomes one part of a clearer guardrail chain.

### 13.1 Input guard

Before backend query:

- Agent kind may call this tool;
- `limit` is capped server-side;
- timestamps parse successfully;
- query time range is inside the RCA100 case window accepted by the runtime;
- required IDs (e.g. `traceId`) are bounded strings;
- arrays have server-side max sizes independent of model schema.

### 13.2 Output guard

Before returning result to LLM:

- bound row/sample count;
- bound serialized character size;
- Evidence schema validates;
- do not leak filesystem paths or answer-key paths;
- raw result references are opaque `rawRef` values.

ToolGuard must not infer root cause.

## 14. Error taxonomy

Introduce typed task errors rather than arbitrary strings where practical.

Minimum codes:

```text
TASK_TIMEOUT
TASK_CANCELLED
TASK_TOOL_BUDGET_EXCEEDED
TASK_TURN_BUDGET_EXCEEDED
TASK_EVIDENCE_BUDGET_EXCEEDED
TASK_AGENT_ERROR
TASK_TOOL_ERROR
TASK_INVALID_CONTEXT
```

Errors shown to the UI may have a short user-facing message, while logs keep the detailed cause.

## 15. Events and tracing

Add task lifecycle events:

```text
task.created
task.started
task.completed
task.failed
task.cancelled
task.timed_out
```

Every relevant server event SHOULD carry:

```ts
{
  investigationId,
  runId,
  taskId?,
  agent?,
  toolCallId?,
  evidenceId?
}
```

This metadata should also be suitable for the existing Langfuse integration, but v8.1 does not require a new tracing backend.

## 16. AgentManager responsibilities after v8.1

`AgentManager` SHOULD be narrow:

- own/reuse specialist Pi AgentSession semantics;
- run one task with an already-built context;
- translate Pi runtime events into task metrics;
- abort the session when requested;
- return `AgentTaskResult`.

It SHOULD NOT own:

- global scheduling;
- Evidence selection policy;
- investigation persistence;
- generic query caching.

## 17. Retry policy

Do not create retry multiplication.

### Pi retry

Owns provider-level transient errors such as rate limits / temporary provider failures.

### Tool retry

Not generalized in v8.1. RCA100/DuckDB is local and read-only; retry only if a concrete transient failure is identified.

### Task retry

Default `maxAttempts = 1` in v8.1. A later milestone may rerun interrupted tasks after error classification is explicit.

## 19. Compatibility requirements

v8.1 MUST preserve:

- Pi dependencies pinned at `0.86.1`;
- RCA100 `t039` one-click recommended demo;
- real DuckDB-backed tools;
- Coordinator-centered orchestration;
- Specialist tool isolation;
- current Pi-chat visual language;
- Ground Truth isolation.

## 20. Definition of done

All conditions are required:

1. `AgentTask` is visible in runtime state and lifecycle events.
2. Scheduler serializes same-Agent work and permits cross-Agent concurrency.
3. Hard `maxToolCalls` and timeout are test-covered.
4. ContextBuilder is the only specialist cross-Agent context assembly path.
5. Abort propagates to queued/running specialist tasks.
6. Tool input/output guards are test-covered.
7. Task events contain correlation IDs.
8. Existing t039 runtime still reaches a final RCA when the model/data environment is healthy.
9. No v8.2 persistence/resume functionality is accidentally mixed into v8.1.
10. `docs/v8.1-harness-tasks.md` is updated to reflect actual completion and deviations.
